# schedule-sending — Paseo plugin design

Date: 2026-09-30
Target: Paseo daemon/app 0.10.1 (local daemon, Claude provider)
Status: awaiting user review

## 1. Purpose

Let a user queue a message into an **existing** Paseo agent chat and have it delivered at a
chosen later time, while the user is away or asleep. This is distinct from Paseo's built-in
Schedules feature, which creates a new chat per run.

Motivating pain: the user hits the Claude 5-hour quota window shortly before bed. The chat sits
idle until morning even though quota resets during the night. With this plugin the user queues
"continue the refactor" for a time after the reset, and wakes to progress in the same chat.

### Success criteria

- User queues a message for a future time from the chat's composer in a few seconds, on desktop or mobile.
- The message is delivered into that same chat at (or shortly after) the chosen time, with the Paseo app closed.
- Pending, sent and failed messages are visible and pending ones can be cancelled.
- A queued message is never silently dropped: it is sent, or it is shown as failed with a reason.
- Queued messages survive a daemon restart and plugin reload.

### Non-goals (v1)

- Recurring schedules (one-shot only).
- Other triggers: on-quota-reset detection, auto-retry after a rate-limit turn failure, "after current turn".
- Attachments/images (text only).
- Slash command, Command Center item, sidebar surface listing all chats.
- Timeline row on send (the sent message appears as a normal user message).
- Detecting that a delivered message hit a quota limit. The user picks a time after the reset.
- Waking a sleeping machine (see Known limits).

## 2. Approach

Daemon-owned queue. The plugin's **server** runtime (a daemon subprocess that runs with no app
connected) owns persistence and firing. The **client** runtime is UI only and talks to the
server through three RPCs.

Rejected alternatives:

- Settings-document store (`defineSettings`): the client writes, the server can only `read()` and
  `subscribe()`. The server cannot persist `sent`/`failed` status, so history and retries would break.
- Client-side timers: stop when the app closes or the phone locks, which defeats the purpose.

## 3. Data model

One record per scheduled message (Zod schema in `shared/schedule.ts`):

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Generated by the server. |
| `agentId` | string | Target chat. |
| `text` | string | 1–10,000 chars. |
| `fireAt` | integer | Epoch ms. Computed by the client in the user's timezone; the server never handles timezones. Must be within 30 days of creation. |
| `createdAt` | integer | Epoch ms. |
| `status` | `pending \| sent \| failed \| canceled` | |
| `attempts` | integer | Send attempts that threw. |
| `nextAttemptAt` | integer? | Set after a failed send attempt (backoff). |
| `lastError` | string? | Last failure reason, shown in the UI. |
| `sentAt` | integer? | Epoch ms of acceptance by the daemon. |
| `finishedAt` | integer? | Epoch ms when the item reached `sent`, `failed` or `canceled`. Drives 7-day pruning. |

## 4. Server runtime

### 4.1 Store (`server/store.ts`)

- File: `<PASEO_HOME>/plugin-data/schedule-sending/queue.json`; fall back to `~/.paseo` when `PASEO_HOME` is unset.
- Writes are atomic (write temp file, then rename). All mutations are serialized through one promise chain.
- Finished items (`sent`, `failed`, `canceled`) are pruned 7 days after they finish.
- A corrupt or unparseable file is copied to `queue.corrupt-<timestamp>.json`, the store starts empty, and the error is logged. The plugin does not crash-loop.

### 4.2 Scheduler (`server/scheduler.ts`)

One `setInterval` tick of about 10 seconds, not one `setTimeout` per item. Reasons: it catches up
after machine sleep or a clock jump, and it avoids the ~24-day `setTimeout` limit.

**Agent gateway availability.** `PluginServerContext` exposes no `paseo` SDK object; only RPC
handlers and lifecycle hooks receive one. The scheduler therefore holds a swappable gateway that
is replaced by the newest `paseo` seen in any RPC handler call or in the `agent.turn_started`,
`agent.turn_ended` and `agent.created` hooks. Until the first one arrives after a plugin start,
ticks do nothing. Each of those hooks also triggers an immediate tick, so a message that became
due while the plugin was starting is delivered as soon as any agent activity or app request occurs.

**Ordering.** Per agent, only the head item (earliest `fireAt`, then `createdAt`) is considered,
and at most one item per agent is sent per tick. A later item never overtakes an earlier pending
one, and two items due together are never sent back-to-back into an agent whose turn has not yet
been reported as started.

Each tick, for the head pending item of each agent, when `fireAt <= now` and (`nextAttemptAt` unset or `<= now`):

1. Refresh the agent (`paseo.agents.ref(agentId).refresh()`). If it no longer exists or is archived, set `failed` with reason "agent archived or not found".
2. If the agent has an active turn, skip the item and try again next tick (wait for idle).
3. Otherwise call `send(text)`.
   - Accepted: set `sent`, record `sentAt`.
   - Threw: increment `attempts`, record `lastError`, set `nextAttemptAt` using backoff 30 s, 2 min, 10 min, 30 min. After 5 failed attempts set `failed`.

**Lookup outages (added after final review).** If the agent refresh itself throws (daemon or bridge
connection down), that says nothing about the message, so it does not use up the send attempts. The
item stays `pending`, `lastError` records the reason (rewritten only when it changes), and it is
retried every tick. It fails only once `now - fireAt` exceeds 12 hours
(`INFRA_RETRY_WINDOW_MS`). Only `send()` throws count toward the 5 attempts. `lastError` from a
lookup outage is cleared as soon as the agent can be inspected again.

The scheduler takes its clock, timer, agent API and store as injected dependencies so it can be tested with a fake clock.

On plugin load the store is read and the scheduler starts. Overdue `pending` items fire late rather than being dropped.

### 4.3 RPCs (`shared/schedule.ts`, handlers in `server/handlers.ts`)

| RPC | Input | Behavior |
| --- | --- | --- |
| `schedule.add` | `{ agentId, text, fireAt }` | Validates (Zod; text trimmed and non-empty; `fireAt` no more than 5 minutes in the past, to tolerate client/daemon clock skew, and no more than 30 days ahead; agent resolves via `refresh()`), appends a `pending` item, returns it. |
| `schedule.list` | `{ agentId }` | Returns that agent's items: pending sorted by `fireAt`, then finished items from the last 7 days, newest first. |
| `schedule.cancel` | `{ id }` | `pending` becomes `canceled`. Any other status is a no-op that returns the current item (handles the cancel-versus-fire race). |

### 4.4 Logging

Log ids and status transitions only. Never log message text: plugin output is retained in the plugin log tail and in `daemon.log`.

## 5. Client runtime

### 5.1 Pill (`client/pill.tsx`, registered in `index.client.tsx`)

One composer pill per agent, registered from an owned agent-directory subscription following the
documented pattern (replace registrations on each snapshot, abort the observation in entry
cleanup). Label `Schedule`, icon `Clock`, behavior `popover`.

A pending-count badge on the icon is a nice-to-have, only if the custom icon component can call
`useRpc` (the docs say icon components can use plugin hooks). If it cannot, ship without the badge.

### 5.2 Popover (`client/schedule-popover.tsx`)

React Native primitives only. Every `Text` color comes from `theme.colors`; padding and stacking
use `layout.compact`. No DOM APIs.

- Multiline message `TextInput`.
- "When" `TextInput` with quick chips `+1h`, `+5h`, `8am` that fill the field (still editable). `+5h` matches the quota window.
- Live preview under the field: the resolved time and relative delta ("Fires Thu 03:00 · in 5h 12m"), or the parse error.
- `Schedule` button, disabled until the message is non-empty and the time parses to a valid future time.
- **Pending** list: message preview (two lines), fire time, `Cancel`. A retrying item shows "retry N/5 · <lastError>".
- **Recent (7 days)** list: `sent` with time, `failed` with reason. No retry button; the user re-adds.
- The list refetches every 5 seconds while the popover is open and is invalidated after add and cancel (TanStack Query).
- RPC failures render inline in the popover, not only as a toast.

### 5.3 Time grammar (`client/parse-when.ts`)

Pure function `parseWhen(input, now) -> { fireAt } | { error }`. `now` is injected. It does not import React.

| Form | Examples | Meaning |
| --- | --- | --- |
| Relative | `in 90m`, `in 5h`, `in 1h30m`, `+5h` | `now` plus the duration. |
| Clock | `3am`, `3:30pm`, `15:30`, `03:00` | Next occurrence: today if still in the future, otherwise tomorrow. |

Rejected with a specific message: empty, unparseable, in the past, less than 1 minute ahead, more than 30 days ahead.

## 6. File layout

```
schedule-sending/
  paseo-plugin.json
  package.json  tsconfig.json
  index.client.tsx
  index.server.ts
  shared/model.ts            zod schemas, types, constants (zod only)
  shared/rpc.ts              the three RPC contracts (defineRpc)
  client/parse-when.ts       pure time grammar
  client/format.ts           pure time/duration formatting
  client/view-model.ts       pure row/preview helpers for the UI
  client/schedule-popover.tsx  container: queries + mutations
  client/schedule-form.tsx     add form
  client/schedule-list.tsx     pending/recent rows
  client/pills.ts            per-agent composer pill registration
  server/logger.ts  server/store.ts  server/scheduler.ts
  server/gateway.ts          adapts the SDK agent handle to the scheduler
  server/handlers.ts
```
Unit tests sit beside their module as `*.test.ts` and are never imported by an entry.

Created with `paseo plugin init`, then reshaped. `requirements.paseo` is set to the minimum
version that provides the composer-pill button descriptor API used here (start from the version
`init` writes, 0.10.1).

## 7. Known limits (v1)

- **Machine sleep.** If the Mac sleeps, the daemon sleeps and nothing fires; queued items fire late on wake (the tick catches up). The user needs `caffeinate`, a keep-awake app, or power settings for overnight use. The plugin cannot prevent this.
- **No limit-hit detection after send.** If the chosen time is before quota resets, the message is delivered and the turn then fails on the limit. The user chooses a time after the reset.
- **Delivery means accepted by the daemon**, not that the agent replied or succeeded.
- **Restart gap.** After a daemon or plugin restart, firing resumes at the first agent lifecycle event or app RPC (see §4.2). A restart in an otherwise silent night can delay delivery until the first such event.
- **Blocked agent waits.** An agent waiting on a permission prompt has an active turn, so a due message waits until it finishes.
- **At-least-once.** A crash between a successful `send()` and the queue write can deliver the same message again after restart.
- **Server-side store only.** Queue state lives in one file on the daemon machine; it is not synced across hosts.

## 8. Verification points during implementation

These depend on API behavior the public docs do not fully specify. Each is checked with a small
probe before dependent code is written; the fallback is stated.

| Point | Check | Fallback |
| --- | --- | --- |
| `PASEO_HOME` visible in the plugin subprocess | Log `process.env.PASEO_HOME` from a scratch server entry. | Use `os.homedir()/.paseo`. |
| `agents.ref(id).refresh()` exposes `activeTurn` and reports archived/missing agents | Call it against idle, busy and archived agents. | Use `agent.turn_started`/`turn_ended` events to track busy state in memory. |
| A `paseo` object received in a lifecycle hook stays usable after the hook returns (needed for the timer-driven tick) | Save it in a hook, call `refresh()` from a timer 60 s later. | Run all sends only from hook and RPC invocations (tick on every event, no interval). |
| `send()` on an agent that is idle behaves as a normal user message | Covered by the end-to-end run. | None needed; this is the documented primitive. |
| Composer-pill registration per agent from the client entry | Follow the documented owned-subscription pattern. | Register a single workspace-level header button instead. |
| Pending-count badge via custom icon + `useRpc` | Try it. | Ship without the badge. |

## 9. Testing

Test-driven at implementation time.

- **Unit**
  - `parseWhen`: table tests with an injected `now`, including day rollover and every rejection case.
  - Store: atomic write, mutation serialization, pruning, corrupt-file recovery.
  - Scheduler with fake clock and fake agent API: due item sends; busy waits then sends; throw leads to retry with backoff; five failures lead to `failed`; archived agent leads to `failed`; overdue item after restart fires; cancel racing a fire.
  - Handlers: Zod rejection (empty text, oversize text, past/too-far `fireAt`, unknown agent); cancel is a no-op on non-pending items.
- **Integration**
  - `npm run typecheck`; run the `client/` audit grep from the Paseo plugin guide (no DOM APIs).
  - Install into the local daemon; `paseo plugin ls` reports `running` with no error.
  - Schedule a message one minute ahead on a throwaway agent and confirm it lands; repeat with the agent mid-turn; cancel one; reload the plugin and confirm the queue survives.
  - Check the popover at desktop width and compact width, in a dark and a light theme.

### Install gate

Plugins are trusted, unsandboxed code. Before installing, read `pluginsEnabled` from the daemon's
`config.json`. If it is false or absent, stop and get the user's explicit permission before
enabling it (`paseo reload --json`). Do not restart the daemon to load source changes; use
`paseo plugin reload schedule-sending`.
